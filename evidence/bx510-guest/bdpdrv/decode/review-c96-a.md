## Review (FE mailbox + queue machinery, rows A–D)

**Verdict: OK with notes — no blockers.**

- **A — dispatch (315–360):** chk vs IDENTIFY split is safe: chk zeroes `priv+0x280..0x294` before posting (decode §3.3, `.text+0x285c..0x2870`) so `arg==0` selects chk; a real IDENTIFY always carries device=0xa0 → `arg!=0`. ACK keyed on `type==0x10` first is equivalent (decode §3: ack is the only type-0x10 post, w1..w3=0; chk/IDENTIFY w0 both have byte2=0). 0xf7/0x08/default post type-0 completions per §5.2 (silence fix is intentional new behavior; C93–C95 never exercised those codes successfully).
- **B — queue:** post slot `(head+count)%4` with count<4 is always free — no off-by-one. Overflow path redirects to the newest slot and restores count=4, preserving head (defensive only; decoded max outstanding = 2). Key consistency: final retirement (count→0) does **not** advance head, so the next post reuses the stale slot — the chk A→B flow reproduces old `fe_status` behavior exactly (A words, then zeros after the ACK). Re-arm on head-advance fires only when count>0; each bottom-half pass retires exactly one message, so it terminates. Note: retirement keys on *any* `0x5c04c` read; a stray/reordered w3 read with count≥2 would retire early (head still only advances when count>0, and both decoded consumers read w0→w3 in order once — `.text+0x28b8..28d8`, `.text+0x4640..4660`), so this stays a documented residual (map §4), not a defect.
- **C — hard rules:** both satisfied: `bx510_fe_dram_write` precedes `bx510_fe_post` on both payload paths, and words are stored before `fe_irq |= FE_IRQ_MSG` inside `fe_post` (297–309). Hand-traced drain loop: R returns `fe_irq&0x10000` → W1C (`s->fe_irq &= ~val`, 735–739) clears only written bits → next R is 0 → loop exits; a post between R and W is impossible on the single vCPU, and the 0x5c804 write case can never raise. ✓
- **D — reset:** all seven new fields reset (`fe_msg` memset, head=count=0, `fe_irq=0`, `fe_mask=FE_IRQ_MSG`, `fe_dma`, `fe_csr`, `fe_dram_page=0`). Mask default bit16 matches §0 defect #2; port_start's `0xfffffff0` keeps bit16.

Notes (P2): (1) `0x5c800` stores raw — spec row 8's "at minimum 0x10000" is not enforced if the driver ever writes a bit16-clearing value; only decoded write is `0xfffffff0`, so acceptable. (2) `0x242xx`/`0x5c400` index by `(off-base)/4` assumes 32-bit-aligned accesses (consistent with existing device style). Verified `s->identify` is exactly 512 B, so `FE_IDENT_LEN=0x200` is correct.
