Decode of the real Sony `sata_mt85xx_mod.ko` firmware-load path, to answer why
Run C55 reads the FE firmware out of flash successfully and is then rejected
with `[IDE]<sata_mt85xx_SocReadMainCode>Read main partition error !!`.

## 1. Bottom line

1. **The flash read succeeded.** Two independent proofs: (a) the `ECC failed: 0 … /
   Number of bad blocks: 0 …` lines are `MTDRawRead`'s own in-loop progress output
   (`.text+0xa14`, `.text+0xa38`); (b) decisive — `SocVerifyMainCode` is only called
   on the `rc == 0` path (`.init.text+0x2dc..0x2e8`; an `MTDRawRead` failure jumps
   straight to the error print at `0x2f4`), and the verifier's message *does* appear
   in the C55 log. So the NFI/NAND model and the MTD layer did their job.
2. **The firmware *content* was rejected by `sata_mt85xx_SocVerifyMainCode`**, the
   inlined acceptance gate. Its first test reads the first dword of the image and
   rejects `0x00000000` and `0xFFFFFFFF` (`cmp`/`bls` at `.init.text+0x08..0x14`,
   decided deterministically in `sata_decode_flags.py`). An erased NAND region
   gives exactly `0xFFFFFFFF` → the observed
   `[IDE] yifan FE firmware without CheckSum..` → return `-1` → `Read main partition error`.
3. **There is no FE firmware in our flash.** The Sony update this rig is built from
   carries **zero** records for the `fe_bin_1`/`fe_bin_2` partitions (the manifest
   written by `emulator-handoff/firmware.py`; see §6), and `firmware.py` fills every
   non-record byte with `0xFF`. The loader is not looking at the wrong partition — it
   is looking at the right partition, which is blank.

**Confidence:** the acceptance criteria and the failing branch: **VERIFIED** from
instructions + a deterministic flag evaluation + the UART string identity.
The blank-flash cause: **VERIFIED** from the update manifest (0 records) and the
image-builder source. What the *real* FE image contains: **UNKNOWN** — we do not
hold it (see §8).

## 2. How the read path is built (so the error ordering is not misread)

`sata_mt85xx_SocReadMainCode` is **not a symbol** in the module — gcc inlined it into
`sata_mt85xx_init_int_ldr` (`.init.text+0x204`, size 0x584). It keeps its own
`__func__` string (`.rodata+0xc4` = `"sata_mt85xx_SocReadMainCode"`), which is why the
UART prints a function name that does not exist in `.symtab`.

`SocVerifyMainCode` *is* a real symbol: `sata_mt85xx_SocVerifyMainCode.clone.5`
(`.init.text+0x000`, size 0x1f4).

The `init_int_ldr` sequence, with addresses:

| addr | what |
|---|---|
| `.init.text+0x25c` | clear `0xfd05c708 = 0` (FE fast-boot state) |
| `.init.text+0x280` | `bl sata_mt85xx_parse_mtd_table` |
| `.init.text+0x294` | print `[IDE]<init_int_ldr>read internal loader binary` |
| `.init.text+0x29c` | `r4 = *sata_int_ldr_fw` — the 1 MiB staging buffer |
| `.init.text+0x2a8` | `if (*mt85xx_fefwmem_base != 0)` → fast-boot path |
| `.init.text+0x2b4..0x2c0` | `memcpy(sata_int_ldr_fw, mt85xx_fefwmem_base \| 0xC0000000, 0x100000)` — skip flash entirely |
| `.init.text+0x2c8..0x2d8` | `MTDRawRead(&.bss+0x64, 16, 0x100000, sata_int_ldr_fw)` ← **main** |
| `.init.text+0x2dc` | `if (rc != 0) goto main_error` |
| `.init.text+0x2e4` | `SocVerifyMainCode(sata_int_ldr_fw)` ← **the gate** |
| `.init.text+0x2f0` | `if (rc == 0) goto tag_parse (0x36c)` |
| `.init.text+0x2f4..0x30c` | `printk("<%s>Read main partition error !!", "sata_mt85xx_SocReadMainCode")` |
| `.init.text+0x310..0x31c` | `if (*(u8*)(.bss+0x50) == 0) goto fail` — backup-exists test |
| `.init.text+0x320..0x330` | `MTDRawRead(&.bss+0x50, 18, 0x100000, sata_int_ldr_fw)` ← **backup** |
| `.init.text+0x33c..0x348` | `SocVerifyMainCode` again; pass → `0x36c` |
| `.init.text+0x34c..0x364` | `printk("<%s>Read backup partition error !!")` |
| `.init.text+0x6b8..0x6c8` | `[IDE]<init_int_ldr>read internal loader binary failed !!` then `print_err_log("060100000000")` |

Note the two paths into `0x6b8`: **read failure and verify failure are collapsed into
the same user-visible message.** `Read main partition error` therefore means
`MTDRawRead != 0 || SocVerifyMainCode != 0` — it is not, by itself, evidence about
which one failed. The C55 log disambiguates it because the ECC/bad-block summary
lines (which only `MTDRawRead` prints) appear *before* the verifier's message.

The literal `"060100000000"` at `.init.text+0x6c0` is the source of the UART's
`[ErrCode:060100000000]`: the log line cross-confirms we are on this exact branch.

### Partition binding (VERIFIED)

`sata_mt85xx_parse_mtd_table` (`0x2aa4`, size 0x3a4) parses `/proc/mtd` and
`sprintf`s `"/dev/%s"` into fixed `.bss` slots. The mapping is exact:

| tag | `.bss` slot | sprintf site |
|---|---|---|
| `fe_power_curve` | `.bss+0x20` | `.text+0x2cd0` |
| `fe_bin_1` (**main**) | `.bss+0x64` | `.text+0x2cf0` |
| `fe_bin_2` (**backup**) | `.bss+0x50` | `.text+0x2d08` |
| `fe_test_data` | `.bss+0x30` | `.text+0x2d1c` |
| `fe_parameters` | `.bss+0x40` | `.text+0x2d30` |

The backup-exists test at `.init.text+0x314` reads `.bss+0x50` — *the first byte of the
`fe_bin_2` path string* — i.e. "non-empty string" is used as the presence flag.

`MTDRawRead`'s second argument (16 for main, 18 for backup) is **dead in this clone**:
`mov r4, r1` at `.text+0x4d4` is the only read, and `.text+0x598` immediately reloads
`r4` from the stack. Both call sites therefore read **from partition offset 0**, which
the pread offset accumulator (`r4:r5` zeroed at `.text+0x5d8`, `strd` at `.text+0x748`)
confirms.

Partition geometry observed in the guest (C55 UART, `mt85xx_part_tbl_init`, PIT v1):

```
0x00a00000-0x00c00000 : "fe_bin_1"      ← 2 MiB partition, mtd8
0x00c00000-0x00e00000 : "fe_bin_2"      ← 2 MiB backup,    mtd9
```

The driver reads **1 MiB** (`0x100000`) from the start of a 2 MiB partition.

### What `MTDRawRead` actually does (VERIFIED, context for §7)

`.text+0x484` (size 0x658, `clone.6`): `sys_open(path, O_RDONLY)` →
`MEMGETINFO` (`0x80204d01`) → select page/OOB geometry by `oobsize`
(448/224/128/64) and `writesize` (2048/4096) → per eraseblock
`MEMGETBADBLOCK` (`0x40084d0b`) → per page `sys_pread64` into `sata_mtd_read_buf`
then `memcpy` into the destination → an `_IOR('M',18,16)` ECC-status query whose
counters produce the `ECC failed/corrected` and `bad blocks/bbt blocks` lines.
It also `sys_mknod`s the `/dev/mtdN` node if absent (`.text+0x844`, mode `0x2180`).

**Bad blocks are skipped, not zero-filled** (dest advances by bytes copied at
`.text+0x788`, flash offset advances by page) — so the verifier sees a *compacted*
logical image. Our rig reports 0 bad blocks, so compaction is the identity here.

## 3. The acceptance gate: `sata_mt85xx_SocVerifyMainCode`

Argument `r0` = the firmware base (`sata_int_ldr_fw`). Returns **0 = accept**,
**-1 = reject**. Four ordered tests: Test 1 is a hard reject; Tests 2 and 3 are
*leniency escapes that accept*; Test 4 is the real checksum.

### Test 1 — image tag word (`fw[0x0000]`) must not be 0x00000000 / 0xFFFFFFFF

```
.init.text+0x08  ldr  r3, [r0]        ; r3 = first 32-bit word of the image
.init.text+0x0c  sub  r3, r3, #1
.init.text+0x10  cmn  r3, #3
.init.text+0x14  bls  0x38            ; "lower or same" -> checksum path
.init.text+0x18  ldr  r3, [ide_log_en]
.init.text+0x20  tst  r3, #32
.init.text+0x24  beq  0x1bc           ; silent reject
.init.text+0x28  printk(.rodata.str1.4+0x540)   ; "[IDE] yifan FE firmware without CheckSum.."
.init.text+0x30  mvn  r0, #0
.init.text+0x34  pop  {r4,r5,r6,pc}   ; return -1
```

`sub`/`cmn`/`bls` is gcc's range test for "v is neither 0 nor -1". Verified by
executing the ARM flag rules in `decode/sata_decode_flags.py`:

```
   v (fw[0])         v-1   N Z C V  path
0x00000000 0xFFFFFFFF  0 0 1 0   REJECT: 'yifan FE firmware without CheckSum..' (0x18)
0xFFFFFFFF 0xFFFFFFFE  0 0 1 0   REJECT: 'yifan FE firmware without CheckSum..' (0x18)
0xFFFFFFFE 0xFFFFFFFD  0 1 1 0   CHECKSUM PATH (0x38)
0x00000001 0x00000000  0 0 0 0   CHECKSUM PATH (0x38)
0x00000004 0x00000003  0 0 0 0   CHECKSUM PATH (0x38)
```

**This is the branch C55 takes.** Both realistic blank-flash fills (all-0x00 and
all-0xFF) land on it.

### Test 2 — checksum word at `0xC100` (leniency escape → **accept**)

```
.init.text+0x38  mov  r3, #49408      ; 0xC100
.init.text+0x3c  ldr  r3, [r0, r3]
.init.text+0x40  cmp  r3, #0
.init.text+0x44  beq  0x19c
... 0x19c: printk(.rodata.str1.4+0x5f8) "[IDE] FE firmware without CheckSum.."
    0x1b4: mov r0, #0 ; return 0     ; ACCEPTED
```

An image with a zero checksum word is **accepted** with a warning. (Note the
distinct string: `yifan FE firmware without CheckSum..` rejects; plain
`FE firmware without CheckSum..` accepts. Two different strings —
`.rodata.str1.4+0x540` vs `+0x5f8` — easy to conflate in a log.)

### Test 3 — header revision byte at `0xC008` (leniency escape → **accept**)

```
.init.text+0x48  ldr  r3, =0xC008
.init.text+0x4c  ldrb r3, [r0, r3]
.init.text+0x50  cmp  r3, #35
.init.text+0x54  bls  0x19c           ; <= 35 -> same "without CheckSum" ACCEPT
```

### Test 4 — checksum: body sum + header word must equal a hardcoded magic

Only reached when `fw[0] ∉ {0,-1}`, `fw[0xC100] != 0`, and `fw[0xC008] > 35`.

Each region is summed as **big-endian** 32-bit words
(`ldrb [b1]; ldrb [b0]; ldrb [b3]; ldrb [b2]` then `(b0<<24)|(b1<<16)|(b2<<8)|b3`,
the loop body at `.init.text+0x7c..0xa8`):

| region | loop setup | bytes |
|---|---|---|
| A `[0x00000, 0x04000)` | `0x70`..`0xa8` | 16 KiB |
| B `[0x07C00, 0x0C000)` | `0xac`..`0xe0` | 17 KiB |
| C `[0x10000, 0xF0000)` | `0xe4`..`0x118` | 896 KiB |

```
.init.text+0x11c  ldr  r3, =0xC101 ; r1 = 0xC102 ; r12 = [r4 + 0xC100]
.init.text+0x148  orr  r1, r3, r1, lsl #8       ; r1 = BE32(fw[0xC100..0xC103])
.init.text+0x14c  ldr  r3, =0x37922226          ; THE MAGIC
.init.text+0x150  add  r1, r2, r1               ; total = body_sum + header_word
.init.text+0x154  cmp  r1, r3
.init.text+0x15c  bne  0x180
... 0x160: return 0 ; printk(+0x5a4) "[IDE] FE firmware CheckSum OK !!"
    0x180: printk(+0x5c8) "[IDE] FE firmware CheckSum Failed : 0x%x !!" ; return -1
```

So the stored word is a **complement**: `fw[0xC100] = (0x37922226 - body_sum) mod 2^32`.
`0x37922226` occurs **exactly once** in the whole module (file offset `0x8214`) — a
compile-time constant, not a per-image field. The image is built so that body +
header == magic ("sum-to-magic"), the classic firmware integrity idiom.

**No size check, no separate-partition checksum, no per-record CRC.** The only
"size" is structural: `MTDRawRead` is always asked for `0x100000` and the regions
above are fixed offsets.

## 4. Firmware image layout the loader expects

Derived from the verifier (checksum gaps + header field offsets) and the tag parser
at `.init.text+0x3ac`. Offsets are within the 1 MiB the driver reads from
`fe_bin_1`.

```
fe_bin_1 (partition 0x00a00000, 2 MiB) — driver reads first 0x100000
  0x00000 - 0x03FFF   boot code, 16 KiB          [checksummed, region A]
                      fw[0] = image tag word (must not be 0 / 0xFFFFFFFF)
  0x04000 - 0x07BFF   not checksummed
  0x07C00 - 0x0BFFF   region B, 17 KiB           [checksummed]
  0x0C000 - 0x0C007   not checksummed
  0x0C008             header revision byte  (<= 34 -> skip tag parse; <= 35 -> accept, no checksum)
  0x0C00C - 0x0C00F   not checksummed
  0x0C010             first FW tag dword
  0x0C014 + 16*i      tag records (see below)
  0x0C100             checksum word, u32 BIG-ENDIAN; total must reach 0x37922226
  0x0C104 - 0x0FFFF   not checksummed
  0x10000 - 0xEFFFF   main FE code, 896 KiB       [checksummed, region C]
  0xF0000 - 0xFFFFF   not checksummed
```

Header fields sit **inside the un-checksummed gap `0xC000..0x10000`**, which is why
the single `0xC100` word can force the total to the magic.

### Tag record format (VERIFIED)

Parsed at `.init.text+0x3ac`..`0x500`. The cursor `r4` is the record **body**;
it starts at `fw + 0xC014` (`add r4,#49152; add r4,#20`) and the tag dword is
read at `[r4-4]`, so tags sit at `fw + 0xC010, 0xC020, 0xC030, …` and each
16-byte record is `{tag, f0, f1, f2}`:

```
+0x00  u32 tag     ASCII, little-endian dword  (e.g. 0x43574f50 = "POWC")   <- [r4-4], tested at 0x3cc
+0x04  u32 BE      f0  (offset within the 1 MiB image)                      <- str at .init.text+0x460
+0x08  u32 BE      f1  (length)                                             <- str at .init.text+0x480
+0x0c  u32 BE      f2  (size field)                                         <- str at .init.text+0x4a4
      byte +0x08   f1's big-endian MSB -> separate flag byte                 <- strb at .init.text+0x4b0
```

Loop terminates when the next tag dword is all zero (`.init.text+0x4cc..0x4fc`).
Recognised tags and their destination globals in `.data`:

| tag | dword | `.data` slot | default `{f0, f1, f2, flag}` |
|---|---|---|---|
| `POWC` | `0x43574f50` | `+0x00` | `{0x10000, 0, 0x400, 2}` |
| `FATB` | `0x42544146` | `+0x14` | `{0x11000, 0xFE000, 0x2000, 1}` |
| `PARM` | `0x4d524150` | `+0x28` | `{0x15000, 0, 0x2000, 2}` |
| `BOOT` | `0x544f4f42` | `+0x3c` | `{0, 0, 0x1000, 3}` |
| `MAIN` | `0x4e49414d` | `+0x4c` | `{0x168000, 0, 0x100000, 0}` |
| `ENCC` | `0x43434e45` | `+0x5c` | `{0, 0x8000, 0x4000, 3}` |

(Unknown tags are silently skipped — `.init.text+0x4cc`. The first three slots are
20-byte records carrying a trailing 4-char name — `.data+0x10` reads `"PWRC"`,
`+0x24` `"FATB"`, `+0x38` `"PARM"` — while the last three are 16-byte records. Note
`PWRC` vs the compared `POWC`: the default name string is a stale spelling and is
never compared; it is only `strncmp`'d later at `.text+0x1a40` while scanning
`.data` for the power-curve section.)

## 5. On success: the full chain to port 0 up

`SocVerifyMainCode` accept → `.init.text+0x36c` reads `fw[0xC008]`:

* `<= 34` → `[IDE] Version 0x%x : do not need parse FW Tag` → straight to `0x6cc`
* `> 34` → `[IDE] Tag Version 0x%x` → tag-record parse → `0x6cc`

`.init.text+0x6cc` re-reads `[0xfd024000+0x34]` — the same flag `init_int_ldr`
tests on entry at `.init.text+0x210` (where non-zero *plus* `0xfd05c704 & 0x601 ==
0x601` means "FE fast boot is done"). Zero here → the SRAM download is needed.
(The register's exact meaning beyond that pairing is INFERRED; the code only shows
the two uses.)

### (a) not yet booted → SRAM boot-code download, `.init.text+0x504`..`0x688`

```
+0x504  if (suspend_to_dram != 0 || .data[0x48] != 3) skip        ; BOOT flag == 3
+0x534  printk("[IDE]download boot code to SRAM (0x%x, 0x%x)")
+0x56c  *[0xfd024188] = 69                    ; (0x45)
+0x570  *[0xfd324180] = 0                     ; FIFO pointer := 0
+0x574..0x590  for i in 0..16384: *[0xfd324180] = i (index) ; *[0xfd324184] = fw[.data[0x40] + i]
+0x58c                     ... and a READ of *[0xfd324184] every iteration (result discarded)
+0x5a4  p = __get_free_pages(0x40d0, 2)       ; 16 KiB readback buffer
+0x5bc  *[0xfd324180] = 0                     ; read-cursor reset before the verify
+0x5cc..0x5d8  for i: p[i] = *[0xfd324184]    ; read back through the same FIFO
+0x5fc..0x640  compare p[i] vs fw[...] ; per-byte mismatch -> "[IDE]SRAM[%04x] WR(0x%02x) != RD(0x%02x)"
+0x644..0x670  printk("[IDE]verify boot code -- %s") with %s = "OK" / "NG"
+0x674  *[0xfd324b00] = 1 ; *(.bss+0x60) = 1  ; loader-done flags
```

This is a **write-then-readback verify** of the 16 KiB boot code into the FE's SRAM
through the FIFO window at `0xfd324180`/`0xfd324184` (phys `0x70324180`/`0x70324184`).
A readback mismatch prints but does **not** abort — execution falls through to the
DRAM download anyway.

**Live-debugger follow-up (VERIFIED): `sram-readback-live.md` in this directory.** The
readback reads `0xfd324184` exactly as decoded, and the model does receive them; the
`RD(0x00)` of every byte is a model FIFO-semantics bug (pop-on-read exhausts the cursor
the `+0x5bc` reset fails to move), not an addressing/decode error.

### (b) `sata_mt85xx_xfer_int_ldr_fw()` (`.init.text+0x688` → `.text+0x1644`)

1. `sata_mt85xx_reset_int_ldr(1)` (`.text+0x1808`), `*[0xfd024030] = 133`,
   `*[0xfd024034] = 0`.
2. **Copies each tag section from the staging buffer into DRAM** (`.text+0x1844`..`0x18e4`):
   `memcpy(dram + sec.off, fw + sec.len_field, sec.size_field)`.

   | destination (offset in DRAM) | source in `.data` |
   |---|---|
   | `dram + BOOT.f0` | `BOOT`, len `BOOT.f2` (`0x1000`) |
   | `dram + MAIN.f0` | `MAIN`, len `MAIN.f2` (clamped to `dram_sz - MAIN.f0`) |
   | `dram + POWC.f0` | power-curve buffer (kmalloc'd, read separately) |
   | `dram + FATB.f0` | FA table buffer |
   | `dram + PARM.f0` | parameter buffer |
   | `dram + 0x20000` | `.bss+0x0`, 32 bytes (power-on params, `sata_mt85xx_PreparePwrOnParm`) |

   The clamp at `.text+0x1878` (`if (f0 + f2 > dram_sz) f2 = dram_sz - f0`, and it
   writes the clamped value back to `.data+0x54`) proves the section table is trusted
   as offsets into the 2 MiB window.
3. `.text+0x1908` **`BSP_CleanDCacheRange(dram, dram_sz)`** — flush the D-cache so the
   FE can DMA-fetch what the CPU just wrote.
4. `.text+0x1938`..`0x19e4` — DRAM wrapper + FE reset release:
   `*[0xfd05c500] = (reserve_base >> 22) & 0xff`;
   `*[0xfd05c600] |= 0x00808080`; `*[0xfd05c604] |= 0x80`;
   `*[0xfd05c804]` read-modify-write (clear default interrupt);
   `*[0xfd05c704] |= 0x601`; `msleep(50)`; `*[0xfd024030] = 0x85`;
   `*[0xfd024034] |= 1`; `msleep(50)`; `*[0xfd05c780] |= 0x103`;
   `*[0xfd05c704] &= ~0x800`;
   `printk("[IDE]release frontend reset done !!")`.
   `0xfd05c704 & 0x601 == 0x601` is exactly what `init_int_ldr` tests at its
   `.init.text+0x21c..0x230` entry gate as "FE fast boot is done".

### (c) `sata_mt85xx_port_start` (`.text+0x2fac`)

Two polls feed the `-EIO` exit:

* **Link state.** `.text+0x30ec..0x3110` polls a register in the ATA window and
  tests `(value >> 16) & 0x3f == 55` (0x37), up to 50 × 10 ms retries, then goes to
  `.text+0x331c` which special-cases the value `34` (0x22). The literal pool carries
  `0xfd00a610` at `.text+0x341c` and the access is `[port+0x10] + 0xfd00a610`-shaped;
  the QEMU model independently implements `case 0xa610 /* LNK_CTRL08: link state
  bits[21:16] */` returning `0x370000` (55) with media and `0x220000` (34) without —
  i.e. **55 = FE link up, 34 = no device**. This is the "frontend ready" the loader
  waits on.
* **Reset/boot handshake.** `.text+0x3144..0x3168` polls `0x7000a01c` until the value
  is `0x50` or `0`, 2500 × 10 ms. Model cross-check: `case 0xa01c /* command/status
  register */`.

The shared failure exit is `.text+0x33f4`, which prints
`[IDE]polling frontend reset interrupt timeout !!` (`.rodata.str1.4+0xe5c`), clears
`_fg_fe_bootup`, and returns `-EIO` (`mvn r0, #4` = `0xfffffffb`) — surfacing as
`platform sata_mt85xx.0: failed to start port 0 (errno=-5)` / `ata_host_activate err`,
which is exactly the C55 tail.

On the success path it sets `_fg_fe_bootup = 1`, assembles `signature` from the ATA
register file and prints
`[IDE]<sata_mt85xx_port_start>ch:%d, i=%d, st=0x%x, signature=0x%x`, then writes
`0x2260733f` into the SATA control window.

> **Not resolved here:** which of the two polls fired the C55 timeout. The log shows
> no `phy_fsm=0x%x` line, and both polls land on the same exit, so this needs two
> MMIO probes (`0x7000a610`, `0x7000a01c`) at `port_start` time rather than a further
> static read.
>
> **Follow-on:** the three `sata_mt85xx_chk_int_ldr` call sites, their retry bounds
> (none in the caller — every poll is bounded), the FE status-mailbox wire format and

## 6. Why our image fails: the partition is blank, not mismatched

The C55 evidence doc (`run-c51-c55.md`) labels the FE firmware "REAL (flash bytes,
sha-pinned via the manifest)". The manifest says otherwise for the FE partitions:

```
# from evidence/bx510-guest/u4-initrd/pulled/manifest.json
fe_bin_1      off=0x00a00000 size=0x00200000 records=0
fe_bin_2      off=0x00c00000 size=0x00200000 records=0
fe_test_data / fe_parameters / fe_power_curve ... records=0
```

(C54/C55 actually ran the rig-derived `/tmp/images-proc` image. Its only change was a
repack of the `rootfs_normal_1` slice — `fe_bin_1`/`fe_bin_2` are untouched by that,
so the `records=0` conclusion carries over unchanged.)

`emulator-handoff/firmware.py` builds `nand.img` from the official Sony update:

```python
# "The updater leaves factory data, bad blocks and untouched sectors
#  unspecified. 0xff means erased in this synthetic installation."
blank = b"\xff" * (1 << 20)
for _ in range(cap // len(blank)):
    flash.write(blank)
for pos in range(bit + 20, bit + bit_len - 20, 20):
    ...  # only BIT records are written
```

`records=0` for `fe_bin_1` ⇒ the sole writes into `0x00a00000..0x00e00000` are the
`0xFF` fill. The Sony **update** does not ship the FE firmware; it is factory-programmed
at manufacture and never part of an OTA image.

Chain, end to end:

1. `nand.img` bytes at `0x00a00000` are all `0xFF`.
2. The NFI model (`emulator-kit/mt8560-nfi.c`) delegates to QEMU's real NAND chip
   (`nand_init(drive_get(IF_MTD,0,0), NAND_MFR_SAMSUNG, 0xda)`), so the read returns
   the actual `0xFF` bytes; ECC status is modelled clean, giving
   `ECC failed: 0, ECC corrected: 0` / `Number of bad blocks: 0, bbt blocks: 0`.
3. `fw[0] = 0xFFFFFFFF` → `SocVerifyMainCode` Test 1 → `-1`.
4. → `Read main partition error !!` (main) → same for `fe_bin_2` →
   `Read backup partition error !!` → `read internal loader binary failed !!` +
   `[ErrCode:060100000000]`.

**So: right file, right partition name, right offset — empty content.** No model
change to the read path is required; nothing in the NFI/MTD/ECC path is implicated.

Note also that on this failure `init_int_ldr` still **returns 0** (`.init.text+0x6c8`
→ `0x690` → `mov r0, #0`) while skipping `xfer_int_ldr_fw`. The shared return prints
`[IDE]<init_int_ldr>init end` (`.rodata.str1.4+0xd40`), which the C55 log shows *after*
the `[ErrCode:060100000000]` block — direct evidence that the fail path returns success
to its caller. The caller cannot tell the load failed; `sata_mt85xx_init` proceeds to
`ata_host_activate`, which is why C55 shows a *later* symptom
(`polling frontend reset interrupt timeout`) rather than a load error.

## 7. The DRAM half: `0xdfc00000` / `0xdd900000`

Neither constant exists in the module. A word-scan of the whole file finds
`0xdfc00000`: 0 occurrences, `0xdd900000`: 0 occurrences. They arrive at run time
through three bdpdrv-provided globals, all `SHN_UNDEF` in this module:

| symbol | value on the C55 rig | set by |
|---|---|---|
| `sata_int_ldr_fw` | `0xdd900000` | bdpdrv `sata_bltin_init_buffer` (1 MiB staging) |
| `svoif_int_ldr_dram` | `0xdfc00000` | bdpdrv `_get_static_buffer` / SVOIF init |
| `svoif_int_ldr_dram_sz` | `0x200000` | same (2 MiB window) |

Printed by `sata_mt85xx_init` at `.init.text+0x858`
(`[IDE]----- frontend FW buffer = 0x%x, DRAM Addr = 0x%x -----`, operands from
`.init.text+0x844/0x850`).

**Who consumes the DRAM copy:** nobody in the driver. There is no read-back and no
mirror-to-controller-visible address — the driver `memcpy`s into DRAM and then
**`BSP_CleanDCacheRange(dram, dram_sz)`** (`.text+0x1908`), i.e. it makes the copy
coherent for a bus master and hands the physical address to the FE by releasing its
reset (`.text+0x1938`..`0x19e4`). The SATA/FE block DMA-fetches the firmware itself
from `0xdfc00000`.

Practical consequence for the QEMU work: to reach port-0-up the **FE must exist as a
bus master in the model**. Writing DRAM and pulsing `0xfd05c704 |= 0x601` is all the
driver does; there is no further CPU-side handshake to fake. The `0x7000a01c` /
`0x7000a610` polls in `port_start` are what will fail until something in the model
answers as the FE.

## 8. What would make it pass

### Option A — real FE firmware (correct, and the only way to a *real* port)

Requires a NAND dump from a physical BX510 (the FE image is factory-programmed, absent
from the update, and not derivable from anything we hold). Acceptance then requires
nothing from us: with a genuine image, `SocVerifyMainCode` computes
`body_sum + fw[0xC100] == 0x37922226` and returns 0.

### Option B — labelled synthetic fixture (unblocks the *driver* code paths only)

Deterministically constructible from the criteria above. Minimum viable image:

* `fw[0]` (offset `0x0000`) = any value ∉ {`0`, `0xFFFFFFFF`} — this alone clears Test 1.
* Then **choose one**:
  * *cheapest*: `fw[0xC008] = 0` → "`do not need parse FW Tag`", no tag table needed, no checksum; or
  * *exercise the tag parser*: `fw[0xC008] = 0x24`, `fw[0xC100] = 0`, records at
    `0xC014` in the §4 format → "`FE firmware without CheckSum`" accept; or
  * *exercise the full checksum*: `fw[0xC008] = 0x24`, place records, then
    `fw[0xC100] = (0x37922226 - body_sum) mod 2^32`.

This is honest only if labelled a fixture: it proves the *loader* accepts an image and
lets `xfer_int_ldr_fw` run to its DRAM write — it does **not** make a frontend exist.
Next gates after that, in order, are: the SRAM FIFO readback at `0x70324180/84`
(must return what was written, else `SRAM[%04x] WR(0x%02x) != RD(0x%02x)` and
`verify boot code -- NG`), then the FE reset/DMA, then `port_start`'s `0x7000a610` ==
55 and `0x7000a01c` ∈ {0, 0x50} polls.

## 9. Open questions

1. **What are the real values of `fw[0]` and `fw[0xC008]`?** Unknown without a dump.
   They determine whether a genuine image even enters the checksum path.
2. **Is the hardcoded `0x37922226` shared across models/revisions?** It is per-`fe_bin`
   by construction; a different FE build would carry a different magic, so a
   synthetic fixture built to *this* magic validates this driver only.
3. **`MTDRawRead`'s dead 2nd argument (16/18).** In `clone.6` it is provably unread
   (`.text+0x4d4` → `.text+0x598`). Whether the un-cloned source used it for a debug
   index or a start block cannot be recovered from the binary. Label: inferred-dead,
   not inferred-purposeless.
4. **The `POWC` vs `PWRC` disagreement** between the compared tag (`0x43574f50`) and
   the `.data` default name (`0x43525750`). Harmless for the compare, but it means the
   source's own naming is not a reliable oracle for tag semantics.
5. **`port_start`'s register base.** Several accesses use `[port+0x10]` as a base with
   a folded offset (e.g. `.text+0x2fe8`: `[port+0x10] - 0x3000000 + 0xA400`), while
   others use absolute literal-pool addresses (`0xfd00a610` at `.text+0x341c`).
   `[port+0x10]` is not resolvable statically. The two poll registers named in §5(c)
   are the ones I could corroborate against both the literal pool and the QEMU model;
   the `0xa600`/`0xa400` reset-handling accesses are not fully pinned.
