# Runs C113–C121 — the FA latch, the geometry, the gates, and the daemon goes active

Scope: sr0 block-layer access (C113), the 0x51/0x52 geometry bug (C114),
the missing-`wc` gate-count bug (C117–C119), gates 14/14 + the daemon
running (C120–C121). Decodes: `rc-stale-window.md`,
`daemon-gate-c111.md`, `master-toc-structure.md`.

## C113 — the EIO latch falls (`2e41bcb`)

`dd-eio-loop.md` §6 predicted it: userspace ioctls 0x8532/0x8534 (=0)
clear `isFaMode`/`isBeQuiet` at `sata_mt85xx` channel+0x208/0x218, and
`sr_prep_fn`'s BLKPREP_KILL latch then clears on the next
`sr_test_unit_ready()` == 0. LADDER a2: **first-ever block-layer dd
PASS**. What it exposed next: geometry wrong
(`blkgetsize64=1655709958144`, want 2,179,497,984 = 1,064,208 × 2048).

## C114 — geometry: root cause + model fix

`rc-stale-window.md` (worker-decoded, host-replay-tested): the block
layer sizes `sr0` from `sr.c get_sectorsize`, which keeps
`max_t(cd->capacity, cdrom_get_last_written())`. The real firmware's FE
answers 0x51 READ DISC INFO / 0x52 READ TRACK INFO; our FE model fell
through to FE_PKT_UNKNOWN **bare-success**, so the driver read its own
0xbb-poisoned stack (`last_track=0xbbbb`, `ti[28..31]=0x30300020`) →
1.6 TB. Model fix: FE_PKT_DISC_INFO (36 B) / FE_PKT_TRACK_INFO (32 B)
rows, alloc-clamp extended to 5 opcodes. **C114 confirms
`blkgetsize64=2179497984`** — capacity is exact.

## C114–C119 — the gates that lied

Gates 02 (tmp-writable) and 13 (master-toc) reported "0 B" while the
underlying reads were succeeding the whole time. Root cause (worker,
fixture-validated 12/12 on dash AND era busybox via qemu-arm): the
guest's busybox 1.17.2 `dd` prints a **three-line** report
(`96+0 records in` …), and the gate's `${dd_err%% *}` grabbed `96+0`
→ digit-guard → 0. Secondary defect: `set -u` + unset `mtoc_md5`
killed C119's gate script at line 397 (RC=2). Fix: no dd-report
parsing at all — md5-oracle checks (proves length AND content) +
`ls -l` field-5 size, all variables pre-initialised. Guest rootfs has
no `wc`/`od`/`tr`/`cut` (the C103 `tail` lesson generalised).

Also: the daemon tgz carries its **own** `daemon_gate.sh` — the
C110–C116 fires ran a stale gate copy until the tgz was rebuilt from
the repo file (rebuild recipe: stage → `sh /tmp/rebuild-tgz.sh`).

## C120 — GATES 14/14 PASS

All fourteen of the daemon's startup gates PASS in one fire, including:

- **02 tmp-writable**: 98304 B, md5 `0a9156c4…` == the 98304-zeros
  oracle (md5 proves length and no short write).
- **12 sacd-init**: `0x40105301` → `0x68000000` (the CPSA Connect
  success constant, twice-observed).
- **13 master-toc**: 20480 B, first-8 md5 `161c7c36…` = `SACDMTOC`,
  whole-range md5 `45ccd7df…` == the Firebird fixture oracle
  (`read10_verdict.sh:83`). The daemon's first real disc read returns
  the genuine Master TOC.
- **14 sacd-auth**: `0x40105302` → 0 (AUTH on the emulated CPSA).

## C121 — the daemon RUNS (and the probe went blind, not the daemon)

Daemon launch (`sacd_extract_160 -S`, pid 1078): its own FE reads
appear on the wire — `lba=510×2, 512×8, 520×16` (its own chunking of
the TOC bundle and the fetch past it), then **~8000 GET CONFIGURATION
polls** — the daemon's normal 1 Hz idle loop. `FFDAEMON3` fast-fire
(inline `cat /res/daemon.out`) captured the oracle:

```
SACD Daemon 0.37 active. Client none. SACD disc inserted.
```

`DAEMON_ORACLE` — daemon-wiring.md §2's success oracle — **VERIFIED**.

Two honest findings from the same runs:

1. **The probe pump starves under console flood.** `observe()`'s
   expect loop advances on `/ # ` prompts; the `[IDE]cache_avail…`
   kernel print flood interleaves them, so post-launch commands
   (`sleep 6`, `cat /res/daemon.out`, `echo STUB_DONE`) never ran and
   the run burned its 480 s timeout looking "incomplete". The daemon
   was healthy the whole time. Fix direction: a flood-immune pump
   (marker-based, not prompt-based) — filed as an issue.
2. **The daemon's own install_modules fails EROFS** (`open filed
   ffffffe2` = −30, decoded via `tools/decode_errno.py`). Its
   `tmpnam`→copy→insmod path writes somewhere read-only. Workaround
   VERIFIED: pre-load `sacd_read.ko` ourselves and the daemon proceeds
   (`insmod: File exists` → active). Exact failing path still to be
   pinned (issue filed).
