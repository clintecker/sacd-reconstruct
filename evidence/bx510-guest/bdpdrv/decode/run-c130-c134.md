## C131 — the read-failure case (issue #7 item 2): DECODED (result=0, not <0)

Control-first design: a known-good 510×10 (exact oracle) BEFORE the hostile
reads, a known-good 532104×1 AFTER (daemon survived).

- `1064300 ×4` (92 sectors past EOF): daemon answered **`type=3 result=0`**
  — NOT a negative. This is daemon-socket-protocol.md §4.1's prediction
  confirmed live: past `end2` no branch fires, `block_size` stays stale (zero
  on a fresh connection), the final clamp yields **zero sectors**.
- `1064206 ×4` (straddling `end2`=1064126): same `result=0`.
- `sacdclient` treats `result<=0` as failure → rc=1, zero bytes written — the
  client contract (§9.1: `result==0 → stop the range`) held.
- Post-failure control: exact oracle. No wedge, no poison, daemon healthy.

**Amendment to §9.1's client rule:** the observed failure shape for past-EOF
is `result == 0` (fresh-connection stale `block_size`), not `result < 0`
(`result<0` remains the no-disc/device-error arm). A client that only aborts
on `result<0` would loop forever at EOF; abort on `result<=0`.

## C132 — overlapping clients, the F-1 accept-aliasing experiment: REFUSED,
not corrupted (amends §5's prediction)

Scenario: pre-flight clean control → reactive UI runs its own session, writes
`/res/ui-session.done` → client A rips 532104×1600 (the UI's
`SACD_UI_WATCH_FILE`) → client B connects the moment A's outfile exists.

Observed (uart + UI event log, `evidence/bx510-guest/graphics/ui-c132/`):

- B's session: **`FAIL DISC_OPEN type=1 result=-1`** — the daemon REFUSED the
  second client at the session layer. No crossed traffic, no fd aliasing
  symptom on the wire.
- A's rip: **froze after exactly one 128-sector chunk** (`RIP DONE 128
  sectors` at t=48.0 is the UI's LAST event; no `CLIENT GONE` for A). A's
  outfile: 262144 B, md5 `32ff654a…` — later proven to be STALE buffer bytes
  (§C133 below), i.e. A's own chunk also never completed: A wedged mid-rip
  with the connection still ESTABLISHED.
- The daemon stayed up: post-overlap control read 532104×1 → exact oracle.
- The UI watched all of it live (18 events, 0 dropped, pool frame PASS
  luminance 12.83) — the "regression instrument" role works.

**Amendment to daemon-socket-protocol.md §5:** the accept-slot aliasing is
real in the code, but the OBSERVED behaviour of two concurrent clients is
(E-1) the second client's DISC_OPEN returns −1 and (E-2) the first client
wedges mid-transfer. The practical rule stands: one client at a time.

## C133 → C134 — the 2-channel area read: STALE-BYTES FINDING, MODEL FIX,
then BYTE-EXACT PASS (issue #7 item 4 — Level 0 complete)

First fire (c133) of `bx510_client_d_arearead.sh.in`: 2-channel-track reads
at 845×1, 845×32 and the boundary-straddling 353750×40 all matched their ISO
oracles — but **745×128 and the 600×1600 rip did not**, and 745×128's md5 was
byte-identical to c132's ripA (`32ff654a…`): deterministic wrong bytes.

The FE census (mmio log) settled it in one look:

- every ≤40-sector 2064-framed read completed (`len=… frame=2064 -> phys …
  descriptor DMA`) — including the EDGE read, which the DAEMON split itself
  into `353750×14 + 353764×26` at the area boundary (§4's branch table working
  exactly as decoded);
- every **128-sector** 2064-framed read hit
  `unusable transfer (nsec=128, 2064-byte frames, cap 131072) — answering
  drive error`.

Root cause chain: the daemon's `MAX_PROCESSING_BLOCK_SIZE` chunk is 128
sectors and its encrypted-branch descriptor is **128 × 2064 = 264 192 B in one
piece** (the unmodified module is the ground truth — the real FE must accept
it); the model's `FE_DMA_MAX = 0x20000` (128 KiB) refused it; the module then
served **stale buffer bytes**, `sacd_read_block_raw` mislabelled the failure
as success (c122 lesson 3), and the daemon reported `result=128` with stale
data — the c105 "stale heap" class, now caught by the ISO md5 oracles instead
of being misread as protocol behaviour.

The census evidence is committed: `evidence/bx510-guest/bdpdrv/fe-tail-c133.txt`
(the refusal rows, incl. `lba=745 nsec=128 0x5c404=264192 … unusable transfer
… cap 131072`) and `fe-tail-c134.txt` (the same reads completing:
`lba=745 nsec=128 len=264192 frame=2064 -> phys 14880000 (descriptor DMA)`,
totals 72 FE reads / 0 refusals). The full mmio logs stay VM-side per policy
(`/tmp/bdpdrv-runc13{3,4}.mmio.log`, ~339 MB).

Fix (model-fidelity, one constant): `emulator-kit/player.local.c`
`FE_DMA_MAX 0x20000 → 0x200000` (2 MiB = the block layer's own maximum
request), comment citing the census. Rebuilt on the VM via
`build.sh` (~4 min), re-fired as **c134**:

| read | md5 | oracle | verdict |
|---|---|---|---|
| 845×1 | `9079e1fc…` | = | PASS |
| 845×32 | `1df16354…` | = | PASS |
| 745×128 (track-0 start, full chunk) | `5b5c4f4e…` | = | PASS |
| 353750×40 (boundary straddle) | `dffda49f…` | = | PASS |
| 600×1600 (13-chunk rip) | `2609c51a…` | = | PASS |

c134 FE census: 72 FE reads, **zero** refusals; 128×2064 descriptors complete
(`len=264192 frame=2064 -> phys 14880000`).

**The live-UI proof** (`evidence/bx510-guest/graphics/ui-c134/`, pool PASS
luminance 12.85): the UI's event log carries the whole rip —
`DAEMON CLIENT CONNECT` → `RIP 128/384/640/896/1152/1280 sectors` at ~2 MB/s →
`DAEMON CLIENT GONE` → `RIP DONE 1600 sectors`. The panel shows disc identity,
both area panels and the rip progress while real music sectors flow.

**Retroactive honesty note (wording corrected per review):** no pre-c134
artifact md5-checks any 128-sector read against the ISO — the five c122
client fires each performed exactly one 510×10 TOC read, and the C103-era
`p128.bin` dumps were never oracle-checked (the `04bda8c4…` value quoted in
an earlier draft of this note traces to no artifact and is retracted). At the
old cap, every 128-sector read must have served stale bytes. The honest
standing claim for pre-c134 128-sector reads is "issued and answered";
byte-exactness at 128 sectors is proven only from c134.
